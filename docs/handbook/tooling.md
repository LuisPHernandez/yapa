# Tooling: what is in this project and why

Every tool, config file, and convention added to the project is listed here, with what it does and why we have it. When a PR adds or removes a tool, it updates this file in the same PR.

For how to actually make a change day to day, see [workflow.md](workflow.md).

## Repository layout

```
.github/            GitHub configuration (PR template)
.env.example        Every environment variable, with development values
docker-compose.yml  Development services: backend, PostGIS, Redis
backend/            Django project (uv-managed; settings in backend/config/)
docs/decisions/     One file per important decision
docs/handbook/      This file and workflow.md
docs/ideas/         Temporary notes and plans; files here come and go
```

## Git

### `.gitignore`

Lists files Git must never track: secrets (`.env`), things each machine generates for itself (virtual environments, caches, build output), and editor or OS clutter.

The `.env` rule matters most. It ignores `.env` and every `.env.something` variant, except `.env.example`, which is the committed template with fake values. A secret that reaches GitHub has to be treated as leaked and rotated, even if the commit is deleted afterwards.

### `.gitattributes`

Windows ends lines with CRLF, Linux and macOS with LF. Without a rule, the same file can differ between two machines, which produces diffs where every line "changed", and breaks shell scripts when they run inside Linux Docker containers.

`* text=auto eol=lf` makes Git store and check out every text file with LF on every machine, regardless of each person's local `core.autocrlf` setting. Windows-only scripts (`.bat`, `.cmd`, `.ps1`) keep CRLF, and binary files such as images are marked so Git never rewrites them.

## GitHub

### Pull requests and protected `main`

Nobody pushes to `main` directly. Every change is made on a short-lived branch and merged through a pull request that the other person approves. With two people this still pays off:

- Both of us know all of the code, not just the half we wrote.
- A second reader catches bugs and unclear code cheaply.
- CI gets a place to run before code reaches `main`, so `main` is always deployable.

This is enforced by a ruleset on GitHub (Settings → Rules → Rulesets), not by trust. The ruleset on `main`:

| Rule | Effect |
| --- | --- |
| Restrict deletions | `main` cannot be deleted |
| Block force pushes | History on `main` cannot be rewritten |
| Require a pull request before merging, 1 approval | No direct pushes; the other person must approve |
| Dismiss stale approvals when new commits are pushed | An approval covers only the code that was reviewed |
| Require conversation resolution | Every review comment is answered before merge |

Repository settings that go with it (Settings → General → Pull Requests):

- **Allow squash merging only, with "Pull request title" as the default commit message.** Each PR becomes one commit on `main`, named after the PR, so history reads as a list of changes rather than a list of work-in-progress commits, and reverting a change is reverting one commit.
- **Automatically delete head branches.** Merged branches are removed from GitHub.
- **Collaborators** (Settings → Collaborators) must be added before the ruleset is activated, or nobody can give the required approval.

### PR template

`.github/pull_request_template.md` pre-fills the description of every new PR with three prompts: what and why, how it was tested, and a short checklist.

### Issues and Projects

Work is tracked as GitHub Issues on one Projects board with three columns: To do, Doing, Done. A PR that says `Closes #12` in its description closes the issue and moves the card when it merges. This is all the project management we use.

## Python environment

### uv

uv manages the backend's Python version and dependencies. Its files live in `backend/`:

| File | Committed | What it is |
| --- | --- | --- |
| `.python-version` | Yes | The Python version we both use (3.13). uv downloads it if missing; the system Python is not used. |
| `pyproject.toml` | Yes | The dependencies we asked for, with allowed version ranges |
| `uv.lock` | Yes | The exact version and checksum of every installed package, including indirect ones. Generated by uv; never edited by hand. |
| `.venv/` | No | The packages installed on this machine, rebuilt from `uv.lock` |

Without a lockfile, two machines installing "the same" requirements get different versions of indirect dependencies, and code that works on one fails on the other. With `uv.lock`, both developers, CI and production install exactly the same packages. This holds inside Docker too: an image built without a lockfile can differ from one build to the next.

There is no `requirements.txt`. It would be a second, unlocked list of the same packages that drifts from `pyproject.toml`. If a platform ever needs one, `uv export` generates it from the lockfile.

`uv run <command>` runs a command inside the environment, syncing it first if the lockfile changed, so there is no virtualenv to activate.

The same lockfile is installed in two places: inside the backend image, which is what actually runs, and in `backend/.venv` on each machine, which only exists so the editor can resolve imports and offer autocomplete.

### Django project

`backend/config/` holds the project-level code: settings, root URLs, and the ASGI/WSGI entry points that production servers load. It is called `config` rather than after the project so it is not confused with the feature apps that will sit next to it. `backend/manage.py` is the entry point for Django commands: `uv run python manage.py <command>`.

## Docker

Everything runs in containers, in development and production ([decision 0002](../decisions/0002-runtime-structure.md), [decision 0003](../decisions/0003-development-in-docker.md)).

### `backend/Dockerfile`

The recipe for the backend image, used by every backend process:

1. Starts from the official `python:3.13-slim` image on Debian.
2. Installs GDAL, GEOS and PROJ, the native libraries GeoDjango needs, from Debian's packages.
3. Copies in the uv program and installs the dependencies with `uv sync --frozen`, which installs exactly what `uv.lock` says and fails if the lockfile is out of date.
4. Copies in the code.

The dependencies are installed before the code is copied. Docker caches each step, so changing code reuses the cached dependency layer, and only a change to `pyproject.toml` or `uv.lock` reinstalls packages.

The image's virtual environment lives in `/opt/venv` (set by `UV_PROJECT_ENVIRONMENT`), outside `/app`. In development `backend/` is mounted over `/app`, and that folder contains each developer's own `.venv` for their operating system; keeping the image's environment elsewhere stops the mount from hiding it.

`PYTHONUNBUFFERED=1` makes Python write logs immediately, so they appear in `docker compose logs` as they happen.

### `backend/.dockerignore`

Files left out when building the image: the local `.venv`, caches, `.env` files and the SQLite file. This keeps the image small and stops secrets from being baked into it.

### `docker-compose.yml`

Defines the development services and how they connect:

| Service | Image | Purpose |
| --- | --- | --- |
| `backend` | Built from `backend/Dockerfile` | Django's development server on port 8000. `backend/` is mounted into the container, so code changes reload without rebuilding. |
| `db` | `postgis/postgis:17-3.5` | PostgreSQL 17 with PostGIS 3.5, a version managed providers also offer ([decision 0001](../decisions/0001-self-hosted-database-first.md)). Data is kept in the `db-data` volume across restarts. |
| `redis` | `redis:7-alpine` | Redis, for the background job queue and caching |

- **Service names are hostnames.** Inside Compose's network, the backend reaches the database at `db:5432` and Redis at `redis:6379`.
- **Published ports** let tools on your machine reach the services: the API at `localhost:8000`, the database at `localhost:5444` (not 5432, to avoid clashing with a PostgreSQL installed on the machine), Redis at `localhost:6379`. Inside Compose the database is still on `db:5432`. They are published on all network interfaces, not only `127.0.0.1`, so the other developer can use your running backend over the same Wi-Fi. The flip side is that anyone on that network can reach them too, with the development credentials, so stop Compose on untrusted networks such as public Wi-Fi.
- **The database has a health check** (`pg_isready`), and the backend waits for it to pass before starting.
- **Credentials come from `.env`.** The `db` service takes `POSTGRES_DB`, `POSTGRES_USER` and `POSTGRES_PASSWORD` from it, and the backend receives the whole file as its environment (`env_file`). See [Configuration](#configuration).

## Configuration

Everything that differs between machines or environments (secret key, debug mode, allowed hosts, database connection, later API keys) comes from environment variables, never from code ([decision 0002](../decisions/0002-runtime-structure.md)). The same image then runs in development, staging and production with different variables.

### `.env` and `.env.example`

- **`.env.example`** is committed. It lists every variable the project uses, with safe development values and a comment for each.
- **`.env`** is each developer's own copy, created from the example. It is ignored by Git, so real secrets can never be committed by accident.
- Both live at the repository root, where Docker Compose reads `.env` automatically.

In production there is no `.env` file in the repository; the server or platform sets the variables.

### django-environ

`settings.py` reads the variables through `django-environ`, which converts the text values into the types Django needs:

| Variable | Read as | Example |
| --- | --- | --- |
| `DJANGO_SECRET_KEY` | Required string; Django refuses to start without it | |
| `DJANGO_DEBUG` | Boolean, `False` if missing | `True` |
| `DJANGO_ALLOWED_HOSTS` | Comma-separated list | `localhost,127.0.0.1,192.168.1.20` |
| `DATABASE_URL` | Parsed into Django's `DATABASES` setting | `postgis://yapa:yapa@db:5432/yapa` |

Defaults are the safe production value (`DEBUG` off, no allowed hosts), so a missing variable makes production stricter, never more open. Settings without a safe default, such as the secret key, have no default and stop Django at startup.

`settings.py` does not read the `.env` file itself; Compose passes it in as real environment variables. That keeps one mechanism everywhere: Django only ever reads its environment.

The `postgis://` scheme selects GeoDjango's PostGIS database backend. The PostgreSQL driver is `psycopg`.
